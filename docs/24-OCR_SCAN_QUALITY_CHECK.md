# OCR quality check of the production scan path (2026-10-15)

**Question.** Before the law firm's NAS corpus (profile `diejuristin`) is
ingested: how well does the production OCR path handle *its* scans, and does
ingestion need a pre-processing step (deskew, higher DPI, another OCR engine)?

**Verdict.** The production engine (Docling 2.137 → auto → RapidOCR with
onnxruntime, CPU, no language hint) is **not good enough for the firm's
scans as-is**: on a 20-file / 42-page sample from the NAS it loses a body
sentence, a reference or a value as letter soup on **16 of 42 pages
(38 %)**, including the sentence that names the divorce judgement in an
agreement, the IBAN line of a Honorarnote and four of eight pages of an
employment contract, and it glues tokens (`1030Wien`, `gemäß§§RAO`,
`Rechnungsdatum:17.09.2013`) on most pages. Scan resolution is not the
cause (most of the corpus is 300 DPI; the garbled pages are legible, and
2× upscaling changes nothing on the synthetic control), the recognition
engine is. **Tesseract `deu+eng` on the same 42 pages removes the
letter-soup class on body text (0 glued tokens, 0.99 word recall on the
synthetic control)**, but brings its own, smaller loss class on real
scans: `§` read as `$` or `5`, digits under handwritten ticks, rotated
letterhead text, bleed-through pages. Recommendation: switch the engine
(the change is in [emanuelplopu/MongoDB-RAG-Agent#2](https://github.com/emanuelplopu/MongoDB-RAG-Agent/pull/2)),
add a one-line `§` repair, and re-ingest scans afterwards; no DPI /
deskew pre-processing. Details in "The firm's scans" and
"Recommendation".

Harness: `scripts/ocr_scan_check.py` (no pipeline change). Raw outputs:
`C:\RecallHub-Verify\bench\ocr-scan-sample-2026-10-16\` (`firm_in`,
`firm_out`, `firm_out_tess`, logs; client documents — stays on the server,
not in git). Synthetic dry run: session scratchpad `dryrun/out*`.

**Update 2026-10-16: implemented.** The OCR engine is now a setting
(`OCR_ENGINE`, default `tesseract`; `OCR_LANGUAGES`, default `deu,eng`) and
Tesseract 5 with the German and English packs is part of the base image. On
all 27 synthetic scan pages the planned-fact retention (the `bench._fidelity`
`scan_jpg` number) goes from **0.667 to 0.949**; see "Implemented" at the end.
Already ingested scans keep their old OCR text until they are re-ingested.

## How to run the check (read-only, no Mongo, no ingestion job)

The harness builds the *same* converter the ingestion worker builds —
`src.ingestion.ingest.create_document_converter()` for PDFs and the
`ImageFormatOption` branch of `process_file` for JPG/PNG/TIF — inside the
`recallhub-ingestion-worker` image, so Docling version (2.137.0), OCR
engine (auto → RapidOCR with onnxruntime) and device (CPU: the live
worker has no GPU reservation) are exactly production's.

```powershell
# sample folder: <sample>\firm_in holds the scans (optionally <stem>.gold.txt with the expected text)
$S = "C:\RecallHub-Verify\bench\ocr-scan-sample-2026-10-16"
docker run --rm -v "${S}\firm_in:/data/in:ro" -v "${S}\firm_out:/data/out" -v "${S}\cache:/root/.cache" `
  -v "C:\dev\repos\MongoDB-RAG-Agent\scripts\ocr_scan_check.py:/app/ocr_scan_check.py:ro" `
  --entrypoint python recallhub-ingestion-worker:latest /app/ocr_scan_check.py /data/in /data/out
```

To pull more files from the share without touching the live containers,
mount the CIFS volume into a throwaway container
(`-v recallhub_share_daten:/data/nas:ro`) and copy from there.

(In Git Bash set `MSYS_NO_PATHCONV=1`, otherwise `/app/...` is rewritten to a
Windows path.) Per input file the output folder gets `page_NN.png` (the
scan, for eyeballing), `page_NN.txt` (OCR text of that page, items grouped
by Docling provenance), `document.md` (what production would store as
`content`), `meta.json`; plus `summary.md` / `summary.json`. `meta.json`
records per page: embedded-image DPI (PDF image metadata, or pixels over
placed width; for images the DPI tag or pixels over A4 width), PDF
text-layer characters (a scanner-side OCR layer makes Docling skip OCR for
that area), conversion seconds, counts of amounts / dates /
Geschäftszahlen / norm codes / § references / umlauts, **garbled runs**
(≥ 4 alphabetic tokens of which half have no vowel or ≤ 2 letters — the
letter-soup signature), **merged tokens** (`HandelGmbH`, `Stufe3`,
`Datum:1`), and — with a gold text — word recall, line recall, the missing
words/lines and which amounts/dates/GZ were lost.

What-if knobs (experiments only; unset = production): `--upscale 2`
(resample image inputs), `--ocr-scale`, `--force-full-page-ocr`,
`--lang deu,eng`, `--engine tesseract|easyocr|rapidocr`. The engine must be
installed in the image; see "Variants" for the Tesseract build.

## Side findings about the production path (independent of the NAS)

1. **No model cache in the live worker.** `rag-ingestion-worker` has no
   Docling / HuggingFace / RapidOCR model files (`/root/.cache` holds only
   `ms-playwright`; no `HF_HOME`, no `DOCLING_ARTIFACTS_PATH`, no cache
   volume), and the image ships none either. The first scanned page after
   *every* worker recreate downloads ~500 MB (layout model
   `docling-project/docling-layout-heron`, TableFormer, RapidOCR ONNX
   models) from huggingface.co — in this run 3.9 min at ~2 MB/s before
   the first page converted — and fails outright without internet. Follow-up
   (not done here): a named volume on `/root/.cache` for the worker and
   the backends, or bake the models into `Dockerfile.base`
   (`docling-tools models download`), and mention it in
   `docs/14-OFFLINE_DEPLOYMENT.md`.
2. **CPU only.** Only `embedder-gpu` has a GPU reservation in the live
   Compose; `get_effective_device()` resolves to CPU in the worker. Steady
   state is ~5-7 s per scanned A4 page (layout + OCR), which bounds the
   NAS ingestion: ~500-700 scanned pages per hour per worker.
3. **Engine and language are Docling defaults.** `PdfPipelineOptions()` →
   `OcrAutoOptions(scale=3.0, lang=[], force_full_page_ocr=False)`; the
   auto model picked `rapidocr with onnxruntime` (EasyOCR, Tesseract,
   Nemotron are not installed). No German language hint is passed.
4. `export_to_markdown()` (what production stores) also drops nothing the
   OCR produced here — the losses below are all in the OCR output itself.

### The two loss classes, with examples

1. **Whole lines become letter soup** on text that is perfectly legible in
   the scan (checked by eye on the PNGs). The affected lines are body-text
   lines in the middle of paragraphs; typically one run of 1-2 lines per
   page. The gold line
   `Dienstverhältnis. Es wird auf unbestimmte Zeit fortgesetzt. Dieser Nachtrag fasst die bisherigen`
   came back as `Dienai itiiagteit t it t gig`; `Verwendung: Buchhalterin
   mit Debitorenbuchhaltung und Betreuung der Bürobarkassa` as `Vurusgusg
   usg ug g ssguusa`; on the Ladung `vertreten durch Mag. Dr. Hugo Bader,
   Rechtsanwalt, …` as `Vert  t r en  t  ien`. This is the "long German
   phrases / whole lines dropped" class of the earlier fact-retention
   measurement (0.667 on the 2026-10-14 ingestion), and it is where the
   lost amounts (`EUR 2.300,00`, `EUR 880,00`) and `§ 244` went: they sat
   on a garbled line.
2. **Spaces vanish between tokens**: `Windisch HandelGmbH`, `1110Wien`,
   `BestehendesDienstverhältnis`, `Eintrittsdatum:01.05.2019`,
   `FN348307c`, `Stufe3`, `Geschäftszahl 44 Cg200/25b`, `EUR2`. 4-13 per
   page. Harmless for a human reader, but it breaks exact-value matching
   and BM25 term matching (`Stufe 3`, `FN 348307c`, `44 Cg 200/25b` are
   different tokens), which is why hybrid search on scans under-performs.

Not observed on this sample: umlaut damage, digit substitutions inside
amounts or dates that *were* recognised, table loss (no tables in the
sample), rotation problems (±1° handled).

## Variants (what would a pre-processing step buy?)

| variant | mean word recall | garbled runs | merged tokens | lost special values | s/page |
|---|---|---|---|---|---|
| production (RapidOCR, scale 3) | 0.836 | 9 | 51 | 8 | 5-9 |
| `--upscale 2` (≈ 300 DPI input) | 0.861 | 10 | 48 | 8 | 6-13 |
| `--engine tesseract --lang deu,eng` | **0.992** | **0** | **0** | **0** (49/49 kept) | 5-8 |

Doubling the input resolution changes nothing material: the same lines are
garbled (different soup), the same values are lost, and conversion is
1.8× slower. Deskew is moot (the harness pages are within ±1°, Docling's
layout model is rotation tolerant at that level).

### Loss classes seen on the real scans

Production (RapidOCR), in order of damage:

1. **Body sentences → letter soup on legible pages** (files 01, 05, 07,
   08, 12, 16): the same failure as on the synthetic scans, and it hits
   exactly the sentences a lawyer would search for (the judgement
   reference, the bank line, the clause naming the parties). Not tied to
   resolution: 300-DPI pages fail, 100-DPI pages fail more.
2. **Glued tokens** on nearly every page (`gemäß§§RAO`, `1030Wien`,
   `Rechnungsdatum:17.09.2013`): breaks exact-value and BM25 matching of
   §-references, postcodes, dates.
3. **Upside-down reading of single short lines** (`pun` for `und`, `UO!M`
   for `Wien`): RapidOCR's orientation guess flips on isolated short words.
4. **Scrambled reading order** on a dense single-page form (18).
5. Handwriting: unusable in both engines (expected).

Tesseract (`deu+eng`, Docling `TesseractCliOcrOptions`):

1. **`§` → `$` or `5`** (`$ 94 ÄrzteG`, `$$ RAO`, `5 10 AVG`) — the one
   systematic error that matters for a legal corpus; a regex repair
   (`$`/`5` followed by a number and a law abbreviation → `§`) fixes the
   observed cases.
2. Digits under handwritten ticks or on grey table backgrounds
   (`15:07`, `3683.3`) — RapidOCR got these right.
3. Rotated or mirrored text (letterheads, bleed-through) → soup where
   RapidOCR read it; Docling logged 80 harmless `OSD failed` warnings.
4. Uppercase umlaut/ß in headings (`GEBOHRENBEFREIT`, `STRARENVERKEHR`,
   `KONIGREICH`), and label/value pairs split onto separate lines.

## Recommendation

- **Do not ingest the NAS scans with the current engine if answers are
  expected to quote scanned content.** 38 % of the sampled pages lose a
  sentence or a value; the lost lines are the ones with the facts.
  Retrieval by topic still works (most words survive), but any answer
  quoting an amount, IBAN, Geschäftszahl or clause from a scan is
  unreliable, and the documents must be re-ingested after an engine
  change anyway (the stored `content` is the OCR text).
- **Switch the OCR engine to Tesseract `deu+eng`** — PR
  [emanuelplopu/MongoDB-RAG-Agent#2](https://github.com/emanuelplopu/MongoDB-RAG-Agent/pull/2)
  (configurable `OCR_ENGINE` / `OCR_LANGUAGES`, language packs baked into
  the base image; synthetic fact retention 0.667 → 0.949). On the real
  sample it removes loss class 1 and 2 of the production engine at the
  same speed. Before relying on it, add a **`§` repair** in the ingestion
  text normalisation (`$`/`5` + space + number + ZPO/StPO/AVG/BAO/RAO/
  GBG/ÄrzteG/… → `§`), which covers every observed case.
- **No DPI / deskew pre-processing**: the corpus is mostly 300 DPI, the
  garbled pages are legible, and upscaling was measured to change nothing.
- **Keep the harness in the loop**: after the engine switch, run
  `scripts/ocr_scan_check.py` on `firm_in` (same 20 files) and compare
  `summary.md` against the table above; the `OSD failed` noise and the
  rotated-text cases are the things to watch. If the §/digit cases turn
  out to matter more than expected, the next step is an ensemble (Tesseract
  text, RapidOCR for lines Tesseract returns as soup), not a return to
  RapidOCR alone.
- **Plan the first ingestion as a multi-day job**: ~130,000-160,000
  scanned pages at ~4.5 s/page on one CPU worker ≈ a week of OCR, plus
  ~15,700 JPGs that are mostly photos and still cost 2-6 s each; consider
  skipping images below ~1,000 px or in `Fotos/Bilder` folders, and
  giving the worker a persistent model cache first
  ([emanuelplopu/MongoDB-RAG-Agent#3](https://github.com/emanuelplopu/MongoDB-RAG-Agent/pull/3)).
- Independently: 62,000 `.msg` files and 42,000 legacy `.doc`/`.dot`
  templates dominate the file count; they are outside this note but will
  dominate ingestion time and index noise if not filtered by folder.
- Independently of the engine: give the worker a model-cache volume (side
  finding 1) before the NAS ingestion, or the first scan after each
  restart costs minutes and needs internet.

## Implemented (2026-10-16): configurable engine, Tesseract `deu+eng` by default

### The change

- `backend/Dockerfile.base` (base version 1.1.0) installs `tesseract-ocr
  tesseract-ocr-deu tesseract-ocr-eng` (Tesseract 5.5.0, Debian trixie,
  ≈ 30 MB). Rebuild the base image before the app images
  (`docker build -f backend/Dockerfile.base -t recallhub-backend-base:latest .`;
  the builder stage stays cached, only the apt layer and the venv copy run).
- `OCR_ENGINE` = `tesseract` (default) | `rapidocr` | `easyocr` | `auto`, and
  `OCR_LANGUAGES` = ISO 639-2 codes, default `deu,eng`. Declared identically
  in `src/settings.py` and `backend/core/config.py`, documented in
  `.env.example`, passed through by `docker-compose.yml` for the worker, both
  backends and the `cli` service. The code default is Tesseract, so a Compose
  file without the entries (the hand-maintained live one) gets the new
  engine as well; the entries only matter for overrides.
- `src/ingestion/ingest.py`: `resolve_ocr_config()` → `OcrConfig`,
  `build_ocr_options()` maps it to Docling (`TesseractCliOcrOptions(lang=
  ["deu","eng"])`, `RapidOcrOptions()`, `EasyOcrOptions(lang=["de","en"])`,
  or nothing for `auto`, which keeps `OcrAutoOptions`), `apply_ocr_options()`
  sets it on the pipeline options and logs the resolved engine once per
  process. `create_document_converter()` (PDF path) and the new
  `create_image_converter()` (image branch of `process_file`, previously an
  inline copy) both go through it. An unknown engine name is logged and
  replaced by the default rather than crashing the worker. Tests:
  `backend/tests/test_ocr_engine_config.py` (option mapping only, no model
  downloads).
- The harness now imports `create_image_converter()` instead of copying it,
  so "production" means whatever `OCR_ENGINE` says; `--engine rapidocr`
  reproduces the old behaviour inside the new image.

Exact-value matching could pick up the first three with a normalisation of

### Re-ingestion is required for existing scans

The stored `content` of a scanned document *is* its OCR text and the chunks
and embeddings are derived from it. Changing `OCR_ENGINE` therefore only
affects documents ingested afterwards; scans ingested with RapidOCR keep the
letter-soup lines until they are re-ingested (delete the documents of the
profile or run a full re-ingestion). The same applies to the synthetic
profile: the 0.667 in the live index stays until `bench-ingest --clean` runs
against the redeployed worker.

## Round 2 (2026-10-16): § repair, two OCR experiments, re-test on three samples

Scope of the round: fix Tesseract's one systematic loss class on the real
scans (`§` → `$`/`5`), try the two engine-side levers for the remaining
classes (rotated text / OSD noise; uppercase umlauts) and keep only what
measures better at similar speed, then re-test on the same 20 firm files, a
fresh second NAS sample and the synthetic corpus. Everything ran in a
side-tagged image (`recallhub-ingestion-worker:ocr-round2`, this branch);
the live worker was **not** redeployed in this round.

### 1. `§` repair (kept)

`src/ingestion/ocr_repair.py` turns `$`, `$$` or a lone `5` into `§`/`§§`
when a section number and a statute marker follow: `Abs`/`Z`/`Zi`/`lit`/`ff`,
one of ~60 Austrian law abbreviations (`ZPO`, `StPO`, `AVG`, `BAO`, `RAO`,
`GBG`, `ABGB`, `KSchG`, `ÄrzteG`, …) or a spelled-out `…gesetz`/`…ordnung`
(also after `des österreichischen …`). Amounts (`$ 5.000,00`), `US$ 10 Mio`
and numbers that merely start with 5 (`52 Abs. 1 ZPO`) stay untouched
(`backend/tests/test_ocr_repair.py`). It runs in the ingestion pipeline on
the converted content **and on the Docling document items**, because the
HybridChunker builds chunk text from the items, not from the Markdown; the
harness applies it too (`--no-repair` switches it off). Being a text repair
it only reaches documents ingested after it shipped.

Before/after on the same 20 firm files (42 pages), same image, same engine
(Tesseract `deu+eng`), `firm_out_tess` → `firm_out_round2`:

| | before | after |
|---|---|---|
| `$`/`5`-misread statute references (`$ 94 ÄrzteG`, `$$ RAO`, `5 10 AVG`, `$ 5 Abs 2 KSchG`, `$ 7 Abs.3 des … Patentgesetzes`, `$ 26 Abs.1 Gerichtsgebührengesetz`) | 5 pages, 6 lines | **0** |
| `§` characters in the stored text | 12 | 19 |
| garbled runs / glued tokens / words | 22 / 6 / 5,392 | 22 / 6 / 5,392 (identical: the engine output is deterministic, only the six lines changed) |
| pages with material loss (doc table above) | 5 of 42 | **3 of 42** (digits under handwritten ticks on 01 and 02, bleed-through on 09 p4) |
| wall time, 42 pages | 179 s (incl. first-run model load) | 119 s |

Synthetic corpus (27 scan pages, 117 planned facts, same harness and
metric as `bench5_tesseract`): **0.949 → 0.957** (112 of 117); the
recovered fact is `§ 1096 Abs. 1 ABGB`. The remaining five are the ones
listed under "Result on all 27 synthetic scan pages" minus that one (`m²`,
a stray space in a date, one capital letter, one umlaut, one missing line).

### 2. Rotated text / OSD noise: `force_full_page_ocr` (not kept)

Docling's Tesseract CLI model runs `tesseract --psm 0 -l osd` per OCR
rectangle; on the small rotated letterhead blocks that OSD fails (the 80
`OSD failed` lines per run) and the block comes back as soup. With
`force_full_page_ocr=True` the page is OCRed as one image: OSD noise drops
to 2 lines and the run is faster (119 → 87 s for 42 pages, one Tesseract
call per page) and the rotated letterhead of file 01 is read correctly
(`An die Beteiligten im Schlichtungsverfahren zu dem Aktenzeichen …`,
`MA 25, 1200 Wien, Maria-Restituta-Platz 1`). But it costs more than it
gains elsewhere: garbled runs 22 → 24, glued tokens 6 → 14 (file 09: 2 →
10), words 5,392 → 5,281, and the Energieausweis table of file 02 loses
figures (`3431 Kd` → `A Kd`, `58356` → `32356`, `138117` → `+58117`), i.e.
table cells are no longer OCRed per cell. Rotated letterheads carry no
facts a lawyer searches for; table figures do. **Not kept.** A per-region
OSD fallback (rotate a rectangle whose OSD failed by 90° and retry) would
be the right fix, but it needs a Docling model change, out of scope here.

### 3. Uppercase umlauts: `tessdata_best` models

The Debian packs (`tesseract-ocr-deu`/`-eng`) are the *fast* integer
models (`deu.traineddata` 1.5 MB, `eng` 4.1 MB). Docling exposes no `psm`
setting for the CLI engine, so the lever is the model: the float
`tessdata_best` files (`deu` 8.6 MB, `eng` 15.4 MB, `osd` 10.6 MB, from
github.com/tesseract-ocr/tessdata_best) were overlaid onto
`/usr/share/tesseract-ocr/5/tessdata` and the 20 firm files re-run.
(First attempt with `TESSDATA_PREFIX` pointing at a bare folder failed:
Tesseract then cannot find its `tsv` config and Docling's TSV parser dies
with `KeyError: 'text'` — the config dir must stay.)

| 20 files, 42 pages | fast models (Debian packs, production) | `tessdata_best` |
|---|---|---|
| wall time | 119 s | **164 s (+38 %)** |
| garbled runs / glued tokens / words | 22 / 6 / 5,392 | 18 / 10 / 5,375 |
| class 2, digits under ticks / grey cells (01 `15:07`, 02 `3683.3`, `3431 Kd`) | wrong | **all three right** (`15:00`, `5683.3`, `3491 Kd`) |
| class 4, uppercase umlauts (`KONIGREICH`, `GEBOHRENBEFREIT`, `STRARENVERKEHR`, `EROFFNUNG`) | 4 wrong | 3 wrong (`KÖNIGREICH` right, the others still `GEBUHRENBEFREIT`, `STRARENVERKEHR`, `EROFFNUNG`) |
| `§` references | 19 | 18: file 20 `§ 65 Zi 1 lit c StPO` became **`8 65 Zi …`** — a new misread variant |
| `$`/`5`/`8` misreads left after repair | 0 | 0 (the repair now also covers the `8` form) |

The best models buy the digit class and one umlaut heading at +38 % OCR
time, more glued tokens (6 → 10, file 09) and a new `§` variant. That is
not "better at similar speed", so the fast packs stay the default. **Not
kept**; the `8` form was added to the repair pattern so a later switch (the
float models would need ~35 MB more in the base image and an
`OCR_TESSDATA` setting) does not reopen the § class. The uppercase-umlaut
class is a recognition limit of both model sets; it affects headings only
and did not cost a fact in any sample.

### 4. Fresh second sample (20 files from other case folders)

Second sample, chosen without looking at the files: 300 random `ADVOKAT
Akten` case folders (the 17 already sampled excluded) plus 100 random

(`docker run --rm -v recallhub_share_daten:/data/nas:ro …`); 3,652 PDF/JPG/
TIF candidates, 1,985 of them scans (no text layer on page 1) or images.
From those, one file per case folder with quotas per kind: 4 Honorarnoten /
Kostenvoranschläge, 5 court documents (Bescheide, Klage, Zahlungsbefehl,
Pflegeprotokoll), 3 contracts (1989, 2003 and 2021 among them), 4 "scan"
images and 4 others — 20 files, 45 pages, years 1989-2021, `firm_in2` with
its own `SAMPLE_MANIFEST.json` (client data, stays on the server). Both
engines ran in the round-2 image: RapidOCR (`--engine rapidocr
--no-repair`, the pre-PR production path) and Tesseract `deu+eng` with the

| 20 files, 45 pages | RapidOCR (old) | Tesseract + § repair (new) |
|---|---|---|

| glued tokens | 36 | **16** |
| words recognised | 3,534 | **3,749** |

Where the difference comes from, by file (page texts in the output
folders):

- **Body sentences soup → read.** RapidOCR again loses the sentences that
  carry the facts: the opening line of both Honorarnoten (`ei s n rn n n b
  g n ie wir gemäß dem nachfolgenden L…`, 09 and 10), the Einspruch sentence
  of the Klage (05: `wea en nn n n nn nn e hen Einspruch zu erheben`, 10
  garbled runs on 5 pages), a clause of the 2003 Gesellschaftsvertrag (01:
  `Darp g g n g ng g tse`), the Treuhandvereinbarung (03), the PVA Bescheid
  (04: `Bernt i t t t t r u n`), the 1989 Baupolizei Bescheid (06, 3 runs)
  and the Kostenschätzung (12). Tesseract reads all of these; its remaining
  "garbled" hits are reference lines the heuristic trips on (`007 39 Cg
  64/13z`, `F-UniqaVers/RB / F`), one dotted line (01) and one word (06:
  `Straßenwässer und Sch ä i a`).
- **Glued tokens** halve (36 → 16); the remaining ones are in the
  Kostenschätzung tables (12: 6) and the PVA Bescheid (04: 5).
- **Handwriting** (07, a handwritten Pflegeprotokoll): RapidOCR emits 37
  word-like fragments of noise (`Pat. lal Vw belomnmen moile`), Tesseract
  emits 2 characters. Neither is usable; Tesseract's silence is the
  smaller index-noise problem.
- **Photos (new finding, cost).** Files 14, 18, 19 are phone photos
  (3,408 × 4,624 and 2,448 × 3,264 px, `Bauschäden`, a parking situation)
  with little or no text. RapidOCR spends 2-4 s on them; Tesseract **23-67
  s** each: Docling's `ocr_options.scale=3.0` hands Tesseract a ~140-Mpx
  bitmap and the single full-image OCR call crawls. That is irrelevant for
  A4 scans (~6 s at 300 DPI as before) but matters for the ~15,700 JPGs on
  the NAS, most of which are photos: at ~30 s each that is ~5 days of
  worker time for files that yield no text. Mitigation measured below
  ("OCR scale on images"); the cheaper fix remains skipping photo folders
  (`Fotos`, `Bilder`, `Attachments` with `IMG_*`) or images under ~1,000 px
  at ingestion time.

OCR scale on images (`--ocr-scale 2` instead of Docling's 3.0, the 13
image files of both samples, outputs `firm_img_out_scale2` /
`firm2_img_out_scale2`): the three photos drop from 67 / 29 / 23 s to
34 / 16 / 12 s, the five firm scan images are unchanged or marginally
better (garbled runs 6 → 4, words 395 → 414, 16 → 14 s), but one 300-DPI
towing-company form (file 16 of the fresh sample) comes back **upside
down** at scale 2 (`Bunddejyosqy` for `Abschleppung`): Tesseract's
orientation detection flipped on the smaller bitmap. A global scale change
is therefore not safe; **not changed.** The photo cost is better handled
by not OCRing photos at all (folder / pixel heuristics at ingestion time)
or by a pixel-capped scale per image (scale = min(3, √(80 Mpx / w·h)),
which keeps A4 scans at 3) — a follow-up in `create_image_converter()`,
not done here.

### Verdict

**PR #2 is merge-ready** (engine switch + § repair; 1,201 backend tests
pass, 3 known `fpdf` failures unrelated), and **PR #3 should land with it**:
this branch already contains PR #3's commits (merged to build one base
image), the live images were built from the merged tree, and without the
baked models the first scan after every worker recreate costs minutes and
needs internet. Merging PR #2 therefore closes PR #3 as well. After the
merge: rebuild the `:latest` images from `main`, recreate the worker, and
re-ingest the profiles that hold scans (the stored content is the OCR
text). Still open, in order of value: skip photos / cap the OCR bitmap for
large images before the NAS ingestion (cost, not quality), and a per-region
OSD retry in Docling's Tesseract model for rotated letterheads (quality,
small).
